# xRocket SDK: работа по сессиям

Проект: Python 3.11+, пакет `xrocket`, Current Pay сначала, Exchange после Pay.
История чата не нужна для продолжения. Свежие указания пользователя имеют приоритет.

## Управляемый цикл

Пользователь разрешил координатору создавать отдельные чаты исполнения и review,
контролировать их, возвращать замечания на исправление и после tests + независимого
review автоматически коммитить/отправлять результат в GitHub. Протокол —
`workflow/AUTOPILOT.md`, локальное состояние — `workflow/.autopilot/state.json`.
Только координатор включённого режима управляет циклом. Worker выполняет один ID,
reviewer работает read-only; они не запускают последующие сессии или automations.
Обычная ручная команда «следующая задача SDK» по-прежнему означает одну карточку.
Координатор не меняет tracked файлы, пока worker работает в том же checkout.

## Вход в сессию

1. Прочитай `workflow/STATE.md`, `workflow/DECISIONS.md` и `workflow/tasks.json`.
2. Для «следующей задачи» выполни `python tools/session.py next`: он печатает
   промпт, ничего не меняя. Для конкретного ID — `python tools/session.py prompt ID`.
   Python здесь и далее — `.venv/Scripts/python.exe` на Windows или `.venv/bin/python`
   на Unix; расположение не угадывай, проверь окружение.
3. Прочитай выбранную карточку, handoff этой задачи при продолжении и handoffs её
   прямых зависимостей. Затем только указанные карточкой specs/source/tests.
   Не загружай все карточки, историю и OpenAPI целиком в контекст.
4. Сверь статус с файлами. `tasks.json` — единственная очередь и источник статусов;
   `STATE.md` — краткий текущий контекст; handoffs — датированные свидетельства,
   а не текущая истина. Код/тесты показывают фактическое поведение, spec — целевое.
5. Проверь незавершённые изменения: Git diff/status, если Git есть, иначе осмотри
   рабочие файлы. Корень Git — папка SDK. Чужие изменения не перезаписывай.

## Одна задача — одна сессия

Выбери один ID с завершёнными зависимостями, поставь `in_progress` в `tasks.json`,
кратко обозначь ожидаемый результат и выполни задачу целиком: код, проверки,
самопроверка, документация и handoff. Рутинные решения внутри карточки принимай сам.
Следующую карточку в этой сессии не начинай, даже если осталось время.

Если уже есть `in_progress`, новая сессия продолжает этот ID, когда предыдущая
сессия закончена. Две активные сессии не должны писать один checkout одновременно;
JSON статус не является технической блокировкой.

Мелкая необходимая правка за пределами перечисленных файлов допустима с объяснением.
Если объём существенно вырос, выдели оставшуюся часть в новую карточку с зависимостью,
не переименовывай существующие ID. Текущую отметь done только при выполненном
исходном результате либо явно записанном уменьшении scope и переносе остальных
критериев. Незавершённую работу не маскируй как done ради смены сессии.

## Границы реализации

- `xrocket.pay` и `xrocket.exchange` самостоятельны; `_core` не импортирует продукты.
- Сохраняй существующие public imports и симметрию sync/async. Деньги — Decimal,
  camelCase только в wire aliases; response statuses и неизвестные поля сохраняются.
- В Pay используй Current OAS и документированные overrides. Legacy не смешивай
  с Current, snapshots вручную не исправляй. Дефекты OAS перечислены в `spec/pay-api.md`.
- HTTP pooling, ownership, timeout, отсутствие redirects/неявных retries и изоляцию
  токенов не ухудшай. Не обобщай весь SDK ради ещё не исследованного Exchange.
- Реализация write-методов и offline tests не означает запуск реальных переводов.
  Live tests в обычный pytest не входят. Сеть и секреты не нужны для обычного DoD;
  live финансовые действия выполняются только по явному заданию пользователя.
- Не сохраняй токены, webhook secrets, персональные данные и заголовки авторизации
  в fixtures, промптах или handoffs. Публикация/деплой не входят в очередь по умолчанию.
  Включённому координатору отдельно разрешён push проверенного кода SDK; это не
  разрешает deploy, PyPI release, live выплаты/выводы и прочие денежные действия.

## Проверки и завершение

Для изменения кода: целевые tests, затем один полный offline pytest, Ruff и strict
mypy. Для изменения packaging, зависимостей или экспортов — ещё build. Для изменений
только workflow/docs достаточно `python tools/session.py check` и проверки ссылок;
старые результаты SDK tests не выдавай за новый запуск. Не повторяй уже успешные
проверки без новых изменений или причины. Недоступную обязательную проверку явно
запиши; такая задача не считается полностью проверенной.

Перед финальным ответом:

1. Напиши новый `workflow/handoffs/<ID>-<NN>.md` по template; не затирай прошлый.
   Укажи реальные изменения, решения, команды/результаты, ограничения и точный
   следующий шаг. Номер увеличивай даже при продолжении того же ID.
2. Обнови `handoff` и статус в `tasks.json`: done при выполненном DoD, blocked при
   внешнем препятствии; для незавершённой работы без препятствия оставь in_progress.
3. Обнови краткий `STATE.md`; существенные решения — `DECISIONS.md`, меняющееся
   поведение — соответствующий spec/README. `spec/verification.md` оставь историей
   первого среза, новые результаты записывай в handoff.
4. Запусти `python tools/session.py check`, исправь ссылки/очередь. Заверши ответ
   ссылкой на handoff, статусом и ID следующей доступной задачи, без её исполнения.

Для отдельного review используй `workflow/PROMPTS.md`: review сам по себе не меняет
статус реализации. Для новой внеплановой работы сначала заведи карточку по template.
