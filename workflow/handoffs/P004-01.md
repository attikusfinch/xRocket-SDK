## Решения и контракт

См. [D015](../DECISIONS.md), [контракт Pay](../../spec/pay-api.md).
Источники — сохранённый Current OAS: два точных GET, ChequeResponseDto,
ChequeListResponseDto и вложенные ChequeLink/Callback/UrlResponseDto.

- Обязательны только `chequeId`, `asset`, `links`, `deleted`; `links: {}` валиден.
  `state` optional str, неизвестные state/targetType и дополнительные поля
  сохраняются. Все поля callback, URL и links optional, вложенные объекты типизированы.
- `amount` отсутствует в declared properties OAS: денежный контракт не придуман,
  при появлении это поле остаётся raw extra. `deleted=True` сохраняется без
  интерпретации state. По upstream description list исключает отменённые чеки,
  retrieve может вернуть их; SDK не фильтрует ответ дополнительно.
- List-даты принимают только aware datetime, сериализуются в ISO 8601 через
  `isoformat()` с исходным offset и дробными секундами. Каждая дата optional;
  искусственного ограничения порядка дат нет. Строки/naive datetime отвергаются.
- Target filters парные, request target type/state ограничены GET enums;
  target — строка до 100 символов, пустая разрешена (minLength отсутствует).
  `None` опускается, cursor передаётся буквально, включая пустую строку.
- `limit` — integer 1–1000, bool отвергается: локальная политика SDK,
  согласованная с существующим invoices API, при OAS type number.
- Retrieve требует хотя бы один непустой строковый ID длиной 1–100, сохраняет
  ведущие нули/символы и передаёт оба ID, если заданы оба. Ограничение 50 из
  create не переносится; приоритет `chequeId` не обещается, т.к. GET его не задаёт.
- Использована существующая Pay `CursorPage` / `CursorPagination`, без общей
  абстракции ресурсов и ужесточения прежней optional-total модели.

Optional response поля допускают None по существующему pattern Pay-моделей;
upstream nullability не подтверждена живыми ответами. Новых live overrides нет.
Независимые read-only анализ контракта и review runtime/wiring/export не нашли
actionable проблем. Тесты написал отдельный агент; основной агент прочитал их
и выполнил полный offline набор после завершения файла.
