## Решения и контракт

См. [D016](../DECISIONS.md), [контракт Pay](../../spec/pay-api.md).
Источники — точные GET `/api/v1/payouts`, `/api/v1/payout`,
`AppPayoutResponseDto`, `AppPayoutListResponseDto`, `PayoutCallbackDto`
в сохранённом Current OAS, без обращения к Legacy.

- Обязательны payout_id, target, target_type, asset, amount, status.
  Amount использует существующий Money → Decimal без float. Status/target_type
  остаются str: неизвестные значения и поля сохраняются.
- Client payout ID, description и callback optional; у `PayoutCallback`
  оба поля optional, payload типизирован как object. Optional response поля
  допускают None по существующей политике Pay-моделей. Live nullability
  не подтверждалась, новых upstream overrides нет.
- Даты — aware datetime, ISO 8601 `isoformat()` сохраняет offset/доли секунды.
  Каждая дата optional; порядок дат не ограничен. Строки/naive datetime
  не принимаются по явной политике Python API.
- Payout GET limit в OAS имеет type number без minimum/maximum/default.
  SDK принимает int без bool и **без границ**; 1–1000 из cheques/invoices
  не переносится. Offline проверена передача 0/-1/1001, но это не обещание
  их принятия живым сервером. Cursor opaque, пустая строка сохраняется,
  None queries опускаются. List всегда читает одну страницу.
- Retrieve требует хотя бы один непустой строковый ID длиной 1–100,
  сохраняет нули/символы и передаёт оба при наличии. Ограничение 50 из
  create не переносится; приоритет при двух ID OAS не задаёт.
- Использован существующий CursorPage с прежней optional-total моделью.
  Новых общих абстракций ресурсов и изменений cheque helpers нет.

Независимый read-only анализ контракта и review runtime/wiring/exports:
actionable находок нет. Другой агент написал новый test-файл; основной агент
прочитал его и запустил полный offline набор после завершения файла.
